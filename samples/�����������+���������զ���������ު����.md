# 產品研發流程與專案管理規範

> 適用範圍：研發部、產品部、設計部與測試部
> 版本：v2.0　生效日期：2025 年 3 月 1 日

## 一、敏捷開發節奏

1. 團隊採「兩週一個衝刺（Sprint）」，每週一上午 10:00 召開衝刺規劃會議。
2. 每日站立會議於上午 9:30 進行，每人發言限時一分鐘，聚焦「昨日進度、今日規劃、阻塞事項」。
3. 每個衝刺結束的週五下午舉行 Demo 展示與回顧會議，產出改善行動清單。

## 二、需求與文件撰寫

1. 新功能必須先撰寫 PRD（產品需求文件），由產品主管與技術主管共同評估後才可排入衝刺。
2. 需求規模以 Story Point 估算，任務拆解到「單人兩天內可完成」為原則。
3. 介面變更需附設計稿件連結，並明確標示各互動狀態（正常、停用、載入中、錯誤）。

## 三、版本控制與 Code Review

1. 分支命名規範：新功能 `feature/描述`、修錯 `bugfix/描述`、急修 `hotfix/描述`。
2. 所有程式變更須發起 Pull Request，至少由一位同儕審核通過後才能合併。
3. 嚴禁直接 push 到 main 分支，違反者需於站立會議說明。
4. 審核重點：功能正確性、單元測試覆蓋、資安風險與 API 向後相容性。

## 四、發版與上線流程

1. 發版窗口固定於每週三晚間 22:00，避開白天業務尖峰。
2. 上線前必須通過 CI 全部檢查（單元測試、Linter、資安掃描）皆為綠燈。
3. 上線後由值班工程師盯盤一小時，確認錯誤率與回應延遲無異常後才算完成。
4. 若上線引發嚴重事故，須於 10 分鐘內執行回滾（Rollback），並於隔日提出事故檢討報告。

## 五、技術債管理

1. 每個衝刺保留 10% 時數處理技術債與重構。
2. 技術債項目需登記於看板，並標註影響範圍與預計償還時程。
